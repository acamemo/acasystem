## A4 Alternative da discutere

**Sintesi dell'analisi dell'assistente:** il frontend sul server deriva dal percorso web precedente, mantenuto quando sono stati introdotti i gusci. Non sono due frontend sviluppati separatamente: oggi lo ZIP da pubblicare su GitHub viene estratto dalla stessa immagine server. I client usano GitHub o cache e non dipendono da quella copia come ripiego.

Si può valutare un unico percorso di distribuzione: solo frontend nei client da GitHub, lasciando il server ACA alle API e adattando la produzione dei pacchetti; oppure frontend sul mini PC e gusci che lo aprono, rinunciando alla distribuzione indipendente della UI ai dispositivi. Sono alternative con conseguenze diverse, non decisioni approvate.

Home Assistant Core è già il backend domotico usato da ACA tramite API. Scaricarne i sorgenti è possibile; far girare Core invariato, mantenere una variante modificata e conservare HA OS ufficiale sono scelte diverse. Il repository Core da solo non sostituisce tutto HA OS e il Supervisor. Inoltre il servizio ACA conserva dati e funzioni propri, che non vengono assorbiti automaticamente da Core.

**Valutazione dell'assistente:** partire dall'uso di HA ufficiale e dalle responsabilità minime necessarie ad ACA; valutare una modifica di Core solo davanti a un limite concreto. Dettagli e fonti nel [blocco 1](../blocchi/01-installazione-aca.md), verifiche in [REP-20261029-006](../../reports/REP-20261029-006-discussione-frontend-backend-ha.md). **Sintesi dell'analisi dell'assistente:** scelti per la baseline documentale CFFI **2.0.0**, libffi **3.8.0** statica PIC per il backend CFFI Android e OpenSSL **3.5.9** statica PIC per cryptography. ## A12 Evidenze positive e condizioni del generatore

**Sintesi dell'analisi dell'assistente:** mantenuta la baseline pycparser 2.23. Il tag non comprende ancora Python 3.14 nella CI, ma la PR upstream #581 del settembre 2025 lo aggiunge senza modificare parser/PLY. Il confronto con il tag mostra invariati i sorgenti runtime. Tre job successivi sul ramo Python 3.14 risultano passati (Linux/macOS/Windows), con pacchetto ancora dichiarato 2.23; il workflow ammette prerelease e non prova Python 3.14.10 preciso o Android.

Il contratto usato da CFFI 2.0.0 corrisponde a CParser/parse, errori e nodi AST della 2.23. Non emerge un'incompatibilità concreta con le API CPython 3.14 esaminate. Un precedente upstream cryptography fissa già insieme CFFI 2.0.0 e pycparser 2.23, ma non viene presentato come prova della terna ACA esatta.

Condizioni per il futuro generatore: docstring conservate, ottimizzazione 0 e Python host con GIL come il target. CFFI 2.0.0 può emettere C diverso in base alla modalità GIL del generatore; non è un difetto dimostrato di pycparser. Il parser serve alla generazione C sul computer di build; il normale binding OpenSSL API-mode sul tablet usa il backend nativo. Pycparser resta comunque nel pacchetto Android per rispettare i metadati CFFI.

Definito un preflight futuro di import/versioni, parsing CFFI e generazione effettiva di `_openssl.c` prima dei compilatori.
